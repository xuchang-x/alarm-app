# 周期闹钟通知调度方案

本文档记录周期闹钟（每 N 天）通知调度的技术选型过程与最终方案。

## 问题背景

expo-notifications 原生支持的 trigger 类型有 date（精确日期）、daily（每天）、weekly（每周），但**没有「每 N 天」的 trigger**。需要自行实现周期闹钟的通知调度。

## 候选方案

### 方案 A：批量预调度

创建/修改闹钟时，一次性计算未来 N 天内所有响铃日期，用 date trigger 逐个调度。每次 App 启动时检查并补充。

优势：实现简单、不依赖后台能力、设好即忘。

劣势：受 pending notification 数量限制（iOS 限 64 条/App，Android 无明确限制）。

### 方案 B：滚动调度

只调度最近一次通知。通知触发后，用户点击打开 App 时再调度下一次。

优势：不占用 pending 额度。

劣势：如果用户不打开 App，后续通知就不会触发，对「设好不管」的使用场景不友好。

### 方案 C：混合方案

预调度未来 7-14 次，每次打开 App 时补充，兼顾可靠性和额度限制。

## 最终方案

**方案 A：批量预调度 90 天**，选择理由：

1. MVP 先做 Android，Android 没有 64 条 pending notification 限制，批量调度几百条都没问题
2. 用户使用习惯为「设好就放着，很少打开 App」，需要最大程度保证不依赖用户主动操作
3. 一个每 4 天响一次的闹钟，90 天也只有 22-23 条通知，开销极小

### 调度时机

- 创建/修改闹钟时：清除旧通知 → 计算未来 90 天的响铃日期 → 批量调度
- App 启动时（含点击通知打开）：检查已调度通知是否不足 90 天 → 补充调度
- 调整操作（跳过/加一次）时：取消/新增对应通知 → 重新计算补充

### 通知 ID 规则

通知 ID 格式为 `alarm-{alarmId}-{YYYYMMDD}`（如 `alarm-3-20250626`），确保唯一性且可反查所属闹钟。

### 可靠性保障

- **手机重启**：Android 系统有 BOOT_COMPLETED 机制，expo-notifications 自动恢复已调度通知，不会丢失
- **90 天后**：只要用户在 90 天内至少点击过一次通知（触发 App 启动），就会自动补充。对于闹钟 App 这个前提合理
- **App 被杀**：不影响已调度的通知，本地通知由系统内核管理

### 后续 iOS 适配

iOS 有 64 条限制，届时需升级为方案 C（预调度受限条数 + 打开 App 时补充 + 可选 Background Fetch 兜底）。
