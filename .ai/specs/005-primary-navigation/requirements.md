# 005 - 一级功能导航与设置入口 需求规格

## 产品定位

为闹钟应用建立统一的一级功能切换方式，将「列表」「日历」和未来的「设置」放入固定的底部 Tab，避免使用内容卡片和页面返回按钮混合承担主导航职责。

## 需求背景

当前列表页通过内容区的「查看日历」卡片进入日历，日历页通过左上角「列表」按钮返回列表。两者分别属于内容发现入口和页面级返回入口，视觉位置、交互形式和导航语义不一致。

随着设置页面加入，继续为每个功能单独设计入口会造成以下问题：

- 用户无法形成稳定的页面切换预期。
- 主功能入口可能随着页面内容滚动而消失。
- 页面返回、功能切换和内容快捷入口的职责容易混淆。
- 新增功能时需要重复设计一套不一致的入口样式。

## 调研结论

### 方案比较

| 方案 | 适用情况 | 当前项目评价 |
|---|---|---|
| 底部 Tab | 2~5 个稳定的一级功能，需要频繁切换 | **推荐**。列表、日历、设置符合一级功能定义，入口固定且易发现 |
| 顶部统一分段控件 | 同一功能下的互斥视图，例如日历的月 / 周 / 3天 / 日 | 适合日历内部视图，不适合作为整个 App 的主导航 |
| 侧边抽屉 | 功能数量较多、切换频率较低 | 当前功能数量少，入口隐蔽，暂不采用 |
| 内容卡片互相跳转 | 功能发现、引导或上下文快捷操作 | 可保留为辅助入口，不能承担唯一的一级导航职责 |

### 结论

采用固定底部 Tab 作为一级导航：

- Tab 1：列表
- Tab 2：日历
- Tab 3：设置

「查看日历」可以保留在列表页，作为内容区的快捷入口，但它的行为应等价于切换到日历 Tab。日历页不再使用左上角「列表」按钮作为主要返回方式，顶部区域只承载日历自身的日期和视图操作。

## 目标平台

- iOS / Android 手机竖屏优先。
- 继续使用 Expo SDK 56、Expo Router 和 Managed Workflow。
- 平板暂不单独设计导航形态，但底部 Tab 需要在更宽屏幕上保持可用和视觉居中。

## 功能详述

### 1. 底部 Tab 一级导航

- 所有一级页面显示同一套底部 Tab。
- Tab 固定包含「列表」「日历」「设置」三个入口。
- 每个 Tab 包含图标和中文标题，使用统一的选中态、未选中态、点击反馈和安全区处理。
- 当前页面对应 Tab 必须有清晰的选中态，不依赖页面标题或内容卡片判断当前位置。
- 点击当前 Tab 时回到该 Tab 的根页面，不重复叠加相同路由。
- 从列表进入创建或编辑页时，底部 Tab 可以按产品设计隐藏；返回后恢复列表 Tab 及其状态。

### 2. 列表 Tab

- 列表 Tab 是默认启动页面。
- 保留当前闹钟列表、搜索、筛选、排序和新建闹钟能力。
- 「查看日历」卡片作为列表页内的快捷入口保留。
- 点击「查看日历」后切换到日历 Tab，而不是额外堆叠一层独立返回栈。
- 列表 Tab 需要保留用户最近一次的搜索词、类型筛选、分类筛选、排序方式和滚动位置。

### 3. 日历 Tab

- 日历 Tab 作为与列表并列的一级功能入口。
- 移除左上角「列表」作为主要返回入口，底部 Tab 负责回到列表。
- 日历顶部继续提供当前日期范围、前后翻页和「今天」操作。
- 「月」「周」「3天」「日」属于日历内部视图，继续使用分段控件切换，不提升为一级 Tab。
- 日历 Tab 需要保留用户最近一次的视图模式、日期锚点、选中日期、暂停提醒筛选状态和滚动位置。
- 点击日历实例进入闹钟编辑页，返回后仍停留在日历 Tab 的原状态。

### 4. 设置 Tab

首版设置聚焦 App 级设置，不承载单个闹钟的编辑字段。

#### 通知权限

- 展示当前通知权限状态。
- 未授权时提供申请权限入口。
- 已拒绝或受系统限制时，提供前往系统设置的引导入口。
- 权限状态变化后，返回设置页能够刷新展示结果。

#### 默认提醒

- 提供统一的默认提醒设置入口，供创建新闹钟时使用。
- 首版至少覆盖现有提醒能力中适合全局配置的默认项，例如默认贪睡时长。
- 默认设置只影响后续创建的闹钟，不修改已有闹钟。
- 具体默认字段和取值范围在技术设计阶段根据创建页现有能力确定。

#### 主题

- 提供主题偏好设置入口。
- 首版至少支持当前浅色主题和跟随系统的选择；深色主题是否纳入首版，需要在视觉设计阶段确认完整色板和组件适配后决定。
- 主题变化后，列表、日历、设置和创建/编辑页面应使用同一套主题 Token。

#### 设置状态

- 设置项保存后立即生效，重新打开 App 后保持。
- 设置页面按功能分组展示，避免将通知权限、默认提醒和主题混在同一组无层级列表中。

### 5. 页面状态与返回行为

- 切换 Tab 时保留各 Tab 的最近状态。
- 列表状态包括搜索、筛选、排序和滚动位置。
- 日历状态包括视图模式、日期范围、选中日期、暂停提醒筛选和滚动位置。
- 设置状态包括当前滚动位置和已保存的设置值。
- 创建、编辑等子页面使用当前 Tab 内的页面栈，不改变一级 Tab 的选中状态。
- 从子页面返回时回到进入前的 Tab 和页面上下文。
- 应避免通过连续点击 Tab 或快捷入口产生重复页面栈。

## 数据存储

- 一级 Tab 的最近选择和各 Tab 页面状态需要本地持久化或在进程内可靠保留。
- App 设置需要本地持久化，至少包括通知相关偏好、默认提醒设置和主题偏好。
- 不新增服务端依赖。
- 具体存储结构在技术设计阶段确定，优先复用项目现有的本地 SQLite 能力，并将导航偏好与闹钟业务数据分离。

## 非功能需求

- 底部 Tab 在 iOS 和 Android 安全区内均可点击，不被系统手势区域遮挡。
- Tab 图标和标题在小屏设备上仍清晰可辨，点击区域满足移动端可操作尺寸。
- 一级页面切换应避免白屏和重复加载；已加载页面切回时优先恢复原状态。
- 导航组件的颜色、字体、圆角、间距和按压反馈使用统一设计 Token。
- 主导航、页面返回、内容快捷入口需要有明确的语义和视觉层级。
- 现有闹钟创建、编辑、通知调度和日历计算逻辑不因导航改造改变。

## 不在本需求范围内

- 不新增闹钟类型或修改闹钟调度规则。
- 不在本需求中完成深色主题的完整视觉设计；仅预留主题配置和 Token 扩展能力。
- 不在本需求中确定所有默认提醒字段的最终产品值。
- 不引入侧边抽屉、桌面端导航或多账户切换。

## 验收标准

1. 用户在任意一级页面都能看到同一套底部 Tab，并能在列表、日历、设置之间直接切换。
2. 列表页的「查看日历」快捷入口与日历 Tab 指向同一个日历根页面，不产生重复导航栈。
3. 日历页不再依赖左上角「列表」按钮返回列表，底部 Tab 可以完成切换。
4. 日历的月、周、3天、日属于日历内部视图，切换方式和一级 Tab 在视觉和语义上有清晰区分。
5. 切换 Tab 后，列表筛选/排序、日历日期/视图和设置页面状态能够按要求恢复。
6. 设置页能够展示通知权限状态，并提供申请权限或前往系统设置的入口。
7. 设置页能够保存默认提醒和主题偏好，重新启动 App 后仍然有效。
8. 创建或编辑闹钟后返回时，用户回到原来的 Tab 和页面上下文。
9. iOS、Android 小屏设备上 Tab 不被安全区遮挡，所有入口可正常点击。
10. 现有闹钟、通知和日历相关测试继续通过，导航改造不改变业务计算结果。

## 已确认决策

- 一级入口：底部 Tab。
- 首版设置范围：App 设置，包括通知权限、默认提醒和主题等。
- 切换体验：保留各页面上次状态。
- 路由结构：底部 Tab 作为根级导航，创建和编辑闹钟作为 Tab 外层子页面。
- 状态范围：列表和日历状态在本次打开 App 期间保留，设置项跨重启保存。
- 默认提醒：首版只配置默认贪睡时长，其他默认项后续扩展。
- 主题范围：首版支持浅色和跟随系统，完整深色主题后续补齐。
- Tab 图标：首版先使用现有字体符号，后续替换为正式图标资源。

## 技术设计阶段需要确认

- 设置页默认贪睡时长的可选值、默认值和后续扩展字段，在技术实现时根据现有创建页能力细化。
- Tab 图标正式资源和无障碍标签文案，在视觉资源确定后替换和补全。
