# 任务拆分 (Task Breakdown)

当技术设计完成后，按照以下流程将功能拆分为可执行的开发任务清单。

## 触发条件

技术设计文档（`.ai/specs/{NNN}-{feature-name}/design.md`）已完成，准备进入编码阶段。

## 前置准备

读取以下文档建立上下文：

- `.ai/specs/{NNN}-{feature-name}/requirements.md`：需求规格
- `.ai/specs/{NNN}-{feature-name}/design.md`：技术设计
- `.ai/specs/{NNN}-{feature-name}/prototype/index.html`：交互原型（如有）
- `.ai/context/architecture.md`：项目结构

## 执行流程

### 第一步：确认拆分维度

在拆分前，向用户确认以下偏好（使用结构化问答）：

**粒度偏好**
- 按模块拆（数据库层、通知服务、UI 页面各一个任务）
- 按文件拆（schema.ts、repository.ts 各一个任务）
- 混合拆（核心/复杂模块细拆，简单模块粗拆）

**项目改造**
- 如果技术设计引入了新的项目结构（如从手动路由迁移到文件系统路由），确认是否作为独立任务

**测试策略**
- 是否需要为核心逻辑拆单测任务
- 如果需要，哪些模块需要单测

### 第二步：识别模块和依赖

通读技术设计文档，识别所有需要实现的模块，并理清依赖关系：

1. **基础设施层**：项目结构、依赖安装、类型定义
2. **数据层**：数据库建表、CRUD 操作
3. **逻辑层**：核心算法、业务服务
4. **状态层**：状态管理（串联数据层和 UI 层）
5. **UI 层**：页面和组件
6. **集成层**：跨模块联调、启动流程、收尾

依赖原则：底层模块先行，UI 层依赖状态层，状态层依赖数据层。

### 第三步：编写任务清单

将任务整理为清单文档，输出到 `.ai/specs/{NNN}-{feature-name}/tasks.md`。

每个任务包含：

- **编号**：T1、T2、T3...
- **标题**：简洁描述任务目标
- **目标**：一句话说明这个任务完成后的预期结果
- **产出**：列出具体产出的文件和功能点
- **依赖**：依赖哪些前置任务

文档结构：

```markdown
# {NNN} - {功能名称} 任务拆分

基于 [需求规格](./requirements.md)、[技术设计](./design.md) 拆分的开发任务清单。

## 任务依赖关系

用 ASCII 图或文字描述任务间的依赖链路，让开发者一眼看出执行顺序和可并行的任务。

## 任务清单

### T1 {任务标题}

**目标**：...
**产出**：...
**依赖**：无 / T1

---

### T2 {任务标题}
...
```

### 第四步：确认

将任务清单展示给用户，确认：

- 任务粒度是否合适
- 依赖关系是否正确
- 是否有遗漏的功能点
- 是否需要调整优先级

## 注意事项

- 任务拆分要对齐技术设计文档，不要自行增减功能
- 每个任务应该有明确的「完成标准」——产出文件清单 + 可验证的结果
- 任务之间的依赖要尽量减少，能并行的尽量并行
- 如果某个任务过于庞大（预估超过 2-3 小时），考虑进一步拆分
- 收尾/联调任务放在最后，确保有一个整体跑通的环节
- 测试任务可以和被测模块并行，不需要等所有代码写完
