# 原型设计

这个 Skill 负责在开发前把视觉方向和页面交互做成可比较、可点击的 HTML 原型。它支持三种模式：未确定风格时调研多套方案，已经确定风格时直接延展当前风格，用户要求新样式时同时保留当前风格和新增调研方案。

详细的来源表、方案卡片和 HTML 页面模板见 [references/ui-research-template.md](references/ui-research-template.md)。只有在生成或更新原型时才需要读取该参考文件。

## 触发条件

满足任一条件时使用：

- 用户说「原型设计」「做个原型」「画个交互稿」「做效果图」；
- 用户要求调研几套 UI、开源样式、竞品交互或设计系统；
- 用户要求采用某个已经选定的视觉风格生成新页面；
- 用户明确要求增加新样式，并希望与当前风格比较。

需求规格通常位于 `.ai/specs/{NNN}-{feature-name}/requirements.md`。如果需求文档不存在或内容不足以确定页面范围，先补齐必要的需求上下文，再生成原型。

## 先判断模式

按以下优先级判断，不要把三种模式混在一起：

### 模式 A：未确定风格，先调研

适用于需求中没有明确视觉方案，或用户说「给我几套看看」「调研 UI」「还没确定风格」。

- 默认调研 **5 套**；用户明确指定数量时按用户数量执行。
- 优先选择有公开源码仓库、官方文档和明确许可证的设计系统或组件库。
- 每套方案都要结合当前需求重组出视觉方向，不直接复制第三方产品页面。
- 输出来源链接、许可证、适配范围、适合本项目的原因和主要取舍。
- HTML 中每套方案必须覆盖相同的页面集合，方便横向比较。
- 产出后请用户选择一个方向，再进入技术设计或代码实现。

### 模式 B：风格已经确定，直接延展

适用于用户已经明确说「采用 Eva / UI Kitten」「沿用当前风格」「按这个样式继续做」，或需求文档中存在明确的已确认设计决策。

- 不重复生成多套方案，也不把已确认风格伪装成调研结果。
- 先读取当前原型、需求文档和已有页面，提取颜色、圆角、间距、字体层级、卡片和控件状态。
- 按同一套视觉 token 生成新页面和已有页面的完整状态。
- 仍然保留当前风格的来源说明（如果它来自开源设计系统），但不要求重复扩展调研表。
- 如果用户同时要求「新样式」，切换到模式 C。

### 模式 C：当前风格 + 新样式一起输出

适用于用户说「增加几套」「换几种新样式」「把当前风格和新方案放一起比较」。

- 将当前已确认风格作为第 1 套基线。
- 默认额外调研 5 套新方案；用户指定数量时按用户数量执行。
- HTML 同时展示基线和新增方案，明确标注「当前风格」与「新增调研」。
- 不覆盖当前风格的交互和页面，只增加比较方案。

如果用户只说「做 UI」，但没有说明风格是否确定：读取需求文档、当前原型和代码中的视觉 token；仍然无法判断时按模式 A 执行，并在产出中说明这是默认假设。

## 执行流程

### 第一步：读取现状和页面清单

先读取：

- `.ai/context/AGENTS.md` 和相关项目上下文；
- `.ai/specs/{NNN}-{feature-name}/requirements.md`；
- 如果存在，读取同一 Spec 下的 `design.md`、`research.md` 和已有 `prototype/index.html`；
- 当前代码中的路由页面、公共组件、颜色常量和交互状态。

从路由和需求中整理页面清单。至少检查以下状态是否存在，不要只生成一个列表页：

- 首页/列表页；
- 创建页；
- 编辑页；
- 空状态；
- 加载状态、错误状态、保存失败状态（需求涉及时必须包含）。

页面清单确定后，所有方案必须使用同一组页面和同一组示例数据，差异只来自视觉和交互组织。

### 第二步：选择来源并完成调研

模式 A 或 C 才执行多套调研：

- 优先官方 GitHub 仓库、官方设计系统站点和官方文档；
- 记录仓库/文档 URL、许可证、适配平台和是否能直接用于当前技术栈；
- 如果是 Web 或跨端设计系统，明确标记为「视觉参考」，不要暗示可以直接安装到 React Native；
- 选择具有明显差异的方向，例如 Material、Eva、token 极简、效率工具、时间线或表单优先；
- 对每套方案写出适用场景、优点、限制和套用到当前项目后的具体表现。

默认不调研 5 个相似的颜色换皮。每套方案必须在布局、信息层级、控件形态、圆角/阴影或交互组织上至少有一处可识别差异。

### 第三步：整理调研文档

在 Spec 目录复用或创建 `research.md`，使用以下结构：

1. 调研范围和「只借鉴设计语言、不直接复制页面」说明；
2. 来源表：编号、方案、来源链接、许可证、适配范围、适合项目的原因；
3. 套用到当前项目后的方案列表；
4. 推荐观察点和迁移/实现取舍；
5. 模式 B 或 C 下的当前已确认方向。

更新 `requirements.md` 时只追加或精确修改视觉决策，不覆盖原有功能需求。用户确认方向后，记录「已确认设计决策」，并保留尚未确认的交互问题。

### 第四步：生成单文件 HTML 原型

输出路径固定为：

`.ai/specs/{NNN}-{feature-name}/prototype/index.html`

原型要求：

- 单文件、可直接打开；
- 使用手机外框模拟真机，但不依赖项目运行环境；
- 顶部提供页面切换，至少包含「首页列表」「创建闹钟」「编辑闹钟」「空状态」；
- 需求涉及的加载、错误、保存失败等状态也提供可切换入口；
- 每套方案都有标题、来源链接、许可证和一句适用说明；
- 每套方案都渲染同一组页面，不允许只有列表页；
- 控件可操作：开关、重复方式、星期、日期/周期字段、创建入口和返回入口要有反馈；
- 页面内容只使用需求里已有的能力，不为展示效果虚构新的业务功能；
- 禁用状态通过文字、边框和颜色层级表达，不用整体 `opacity` 让内容透出；
- 深色或浅色主题都要保证文字和控件对比度；
- 页面在窄屏下可以纵向浏览，不出现横向溢出。

如果已有原型文件，优先在原文件上迭代，保留用户已经确认的内容。模式 C 只新增方案和页面，不删除当前风格。

### 第五步：查看、验证和交付

生成后执行：

- 检查 HTML 是否包含所有方案、来源链接和页面入口；
- 检查内嵌脚本语法；
- 打开或展示 HTML 给用户查看；
- 用一句话说明当前模式、方案数量和下一步需要用户确认的内容。

用户确认某套风格后，如果下一步是实际开发，再进入编码流程；本 Skill 本身只负责调研、视觉决策和原型，不默认修改业务代码。

## 交付格式

最终回复至少包含：

- 当前使用的模式（A / B / C）；
- 调研方案数量和来源链接所在文件；
- HTML 原型文件链接；
- 页面清单；
- 推荐方案或需要用户选择的编号；
- 已验证的内容（例如 HTML 脚本语法）。

## 注意事项

- 不要在风格未确认时直接替用户选定一个方案并跳过比较。
- 不要在风格已确认时为了凑数量重新生成多套方案，除非用户明确要求新样式。
- 默认调研数量是 5 套，不是固定上限；服从用户指定数量。
- 来源链接和许可证必须来自可核验的公开页面；不能把自制视觉方向写成第三方官方样式。
- 如果某套方案不能直接用于当前平台，要在调研表和 HTML 卡片中明确说明。
- 原型用于确认视觉和交互，不等同于最终 React Native 实现；不要把 HTML 中的 CSS 直接当成生产代码。
