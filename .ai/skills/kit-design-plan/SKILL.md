# 技术设计 (Technical Design)

当需求文档和交互原型确定后，按照以下流程进行技术设计，最终输出 `design.md` 技术设计文档。

## 触发条件

需求文档（`.ai/specs/{NNN}-{feature-name}/requirements.md`）和原型（`.ai/specs/{NNN}-{feature-name}/prototype/`）已完成，准备进入编码阶段前。

## 前置准备

读取以下文档建立上下文：

- `.ai/context/overview.md`：技术栈和关键决策
- `.ai/context/architecture.md`：项目结构和已有依赖
- `.ai/specs/{NNN}-{feature-name}/requirements.md`：需求规格
- `.ai/specs/{NNN}-{feature-name}/prototype/index.html`：交互原型
- `.ai/rules/coding.md`：编码规范

## 执行流程

### 第一步：识别技术决策点

通读需求文档，列出需要做技术决策的领域。常见决策点包括但不限于：

- 导航方案
- 状态管理
- 数据存储 & 数据模型
- 第三方依赖选型
- 核心算法/调度策略
- 手势/动画方案

将决策点清单展示给用户，确认是否有遗漏。

### 第二步：逐项讨论决策

对每个决策点与用户逐一讨论。每个决策点的讨论模式：

1. **给出 2-3 个候选方案**，简要说明各自优劣
2. **给出推荐方案**并说明理由
3. **让用户确认或选择**

讨论原则：

- 一次聚焦一个决策点，不要混着聊
- 如果候选方案差异不大，直接给推荐方案让用户确认，不需要展开辩论
- 如果某个决策点涉及复杂技术取舍（如调度策略、缓存方案），标记为「重点议题」

### 第三步：深入重点议题

对标记为「重点议题」的决策点做专项讨论：

1. 详细分析各方案的实现路径和风险
2. 讨论边界情况和降级策略
3. 与用户确认最终方案

**重点议题独立沉淀**：如果讨论内容足够深入（超出简单选型），将结论沉淀为独立文档，放在 `.ai/specs/{NNN}-{feature-name}/` 下，并在最终 `design.md` 中引用。

参考案例：[周期闹钟通知调度方案](../../specs/001-alarm-mvp/notification-scheduling.md) 就是一个从技术设计过程中拆出来的独立方案文档。

### 第四步：编写 design.md

将所有决策整合为技术设计文档，输出到 `.ai/specs/{NNN}-{feature-name}/design.md`。

文档结构：

```markdown
# {NNN} - {功能名称} 技术设计

## 技术选型总览
表格形式列出所有选型决策。

## 目录结构
完整的文件/目录结构，说明每个目录的职责。

## 数据模型
建表语句 + 设计说明。

## ID 生成策略
主键和业务 ID 的生成方式。

## [核心机制名称]
引用或内联核心技术方案。如有独立文档则引用链接。

## 状态管理
Store 结构和数据流。

## 导航结构
路由定义和页面跳转关系。

## 手势交互
手势方案和各场景的行为定义。

## 关键流程
用文字描述核心用户流程的技术实现步骤。

## 依赖清单
所有依赖及安装说明。

## 后续考虑
MVP 不做但需要留口子的事项。
```

### 第五步：确认与更新关联文档

1. 将 `design.md` 展示给用户确认
2. 检查并更新关联文档：
   - `architecture.md`：如果技术设计改变了项目结构或核心依赖，同步更新
   - `requirements.md`：如果讨论中发现需求变更（如功能从「后续做」提升到 MVP），同步更新
   - `AGENTS.md`：如果新增了文档文件，更新索引

## 注意事项

- 技术设计要和需求规格、交互原型三方对齐，不要自行增减功能
- 推荐方案要给出具体理由，不要只说「更好」「更强」
- 讨论过程中用户做出的决策是最终决策，如实记录，不要替用户改主意
- 数据模型要包含建表 SQL，不要只画 ER 图
- 重点议题的独立文档应自包含，不读 design.md 也能理解
- 如果项目是 Expo 项目，查阅对应 SDK 版本的文档确认 API 可用性
