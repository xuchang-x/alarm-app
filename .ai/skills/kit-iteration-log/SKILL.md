## 用户输入

```text
$ARGUMENTS
```

## 概述

本项目（alarm-app）用两份互补的日志追踪演进：

| 日志 | 路径 | 更新节奏 | 视角 |
|------|------|----------|------|
| 版本迭代日志 | `docs/iteration/release/{version}.md` | 每次 `package.json` 版本号 bump 后 | 单个版本内的核心变更 |
| 周迭代日志 | `docs/iteration/weekly/{周一yyyyMMdd}-{周五yyyyMMdd}.md` | 每周（通常周五） | 一周内可能跨多个版本的核心变更汇总 |

两份日志**内容来源不同、粒度不同**，不是互相复制关系：版本日志聚焦"这个版本号下改了什么"，周报聚焦"这一周（可能横跨多个版本号）做了什么"。两者若时间窗口有重叠，允许对同一功能点各自用适合自己粒度的语言重新表述，不要求逐字一致。

`$ARGUMENTS` 为空时，默认「版本 + 周报都检测并按需更新」；用户明确只提其中一种（如"更新周报"）时只处理对应的一种。

## 核心写作原则（强制遵守）

这些原则参照 Mainflow Coding Kit 的历史经验固化而来，新增/合并条目时必须遵守，不得退化为"commit 记录翻译"：

1. **面向"变更后的能力效果"写作，禁止逐条翻译 commit message**。素材统一来自 `git log`/`git diff`/`git show` 分析实际代码改动，但成文必须是"这次改完之后 App 多了什么能力、解决了什么问题"，而不是把 commit message 或 diff 摘要罗列出来。同一功能点如果对应多个 commit（如先加功能后修 bug、或分多次提交完成同一件事），合并为一条完整描述，不按 commit 拆分。多个不同的改动如果解决的是相似/关联的问题（如同一模块的多个改进、同一交互流程的不同环节优化），也应合并为一条整体描述。
2. **按「功能迭代」「工程与平台迭代」「文档与规范迭代」三分类组织（固定此顺序），两份日志（版本 + 周报）保持同一套分类原则**，分类依据是**改动所在的目录路径**：
   - **功能迭代**：`src/`、`app/`（含路由、组件、hooks、工具函数）——用户在 App 里可感知的功能变更。
   - **工程与平台迭代**：`package.json`、`app.json`、`tsconfig.json`、`jest.config.js`、`.npmrc`、`assets/` 等依赖、构建、资源配置、原生平台相关变更。注意 `android/`、`ios/` 目录被 `.gitignore` 忽略，其中的改动不产生提交记录，不在素材范围内。
   - **文档与规范迭代**：`.ai/`（specs / skills / rules / context）、`docs/`、`AGENTS.md`、`SDD.md` 等研发过程资产——需求规格、技术设计、skill 工作流、编码规范、开发知识库的演进。
   - 若某个时间窗口内只有一类或两类变更，允许只写对应分类的二级标题，不强行凑齐三类。
3. **同一功能点持续演进时，合并进已有编号小节，而非重复开新编号**：判断依据是"标题/主题是否与已有条目一致或是其直接延续（如同一功能的补丁/修正）"，是则在该小节内追加/改写描述，否则才新增一个编号小节。目标是让读者看到的是"当前状态的准确描述"，而不是"变更历史的流水账"。
4. **精简克制**：只记录用户可感知的核心功能变更（或对研发效率有实质影响的工程/文档变更），不收录纯内部重构、typo 修复、无行为变化的代码整理（除非其本身是本次迭代的主题，如"精简 XX 组件"这类目的就是简化维护成本的改动）。
5. **排除纯外部文档操作**：以下类型的改动**不收录**，即使做了也跳过：
   - 更新学城开发日志（km.sankuai.com/collabpage/2754637875）等外部平台文档
   - 在外部平台创建/修改页面或配置，但本仓库代码/文档本身无对应改动
   - 判断依据：**本仓库内是否有实质变更**——有则收录，只改了外部内容则不收录。
6. **文件名与标题格式必须与历史文件保持一致**（见下方「格式规范」），不得随意发挥新格式。

## 执行步骤

### 1. 确定版本号与周报时间窗口

- 版本号：读取仓库根目录 `package.json` 的 `version` 字段（唯一权威来源，不要从分支名或 `app.json` 猜测；`app.json` 的 `expo.version` 与之保持一致但不是权威）。
- 周报窗口：以今天所在自然周的周一为起点、周五为终点（macOS 用 `date -v-{n}d` 计算，格式 `yyyyMMdd`），拼出文件名 `{周一}-{周五}.md`。若用户明确指定了"上周"，则相应向前推 7 天。

### 2. 检测目标文件是否已存在，分别处理

对 `docs/iteration/release/{version}.md` 与 `docs/iteration/weekly/{周一}-{周五}.md`（按 `$ARGUMENTS` 判断的范围）分别执行：

- **已存在**：完整读取现有内容，识别已有的三分类二级标题及其下编号小节；后续新变更按"核心写作原则 3"判断是合并进已有小节还是新增小节，输出合并后的完整文件内容（不是在文件末尾简单追加）。
- **不存在**：按下方模板从零新建（`docs/iteration/release/`、`docs/iteration/weekly/` 目录不存在时一并创建）。

### 3. 收集本次变更素材

- 确定统计区间：
  - 版本日志：`git log` 中"上一个版本号 bump commit"（message 形如 `chore(构建): 版本号更新至 x.y.z`）到当前 HEAD 之间的提交。
  - 周报：`git log --since="{周一日期} 00:00:00"` 至今的提交（或用户指定的时间窗口）。
- 按路径分别拉取三类改动，作为分类依据：
  - `git log <区间> -- src/ app/` → 功能迭代素材
  - `git log <区间> -- package.json app.json tsconfig.json jest.config.js .npmrc assets/` → 工程与平台迭代素材
  - `git log <区间> -- .ai/ docs/ AGENTS.md SDD.md` → 文档与规范迭代素材
- 对每个区间内命中的 commit，用 `git show`/`git diff` 查看具体改动内容，重点关注实质性变化（新增能力/修复问题/交互调整），忽略纯格式化改动。
- 若工作区同时存在未合并的本地 commit 或未提交改动（`git status`），一并纳入素材范围（视为"本次要记录的内容"的一部分）。

### 4. 按「核心写作原则」组织文案并写入

- 版本日志二级标题固定为 `## 功能迭代` / `## 工程与平台迭代` / `## 文档与规范迭代`（固定此顺序），各自下面用 `### 1. xxx` 编号小节，标题为简短的功能点概括，正文单一改动写一段话，多个子改动用要点列表。
- 周报沿用同样的三分类（同样固定此顺序），标题下用不带编号的二级列表（`- xxx` / `  - xxx`），风格更精简紧凑，不需要像版本日志一样展开成小节。

### 5. 格式规范（必须与历史文件保持一致）

**版本迭代日志** `docs/iteration/release/{version}.md`：

```markdown
# {version}

发布日期：{yyyy-MM-dd}

## 功能迭代

### 1. {功能点标题}

{说明，可为一段话或要点列表}

## 工程与平台迭代

### 1. {功能点标题}

{说明}

## 文档与规范迭代

### 1. {功能点标题}

{说明}
```

**周迭代日志** `docs/iteration/weekly/{周一yyyyMMdd}-{周五yyyyMMdd}.md`：

```markdown
# 本周迭代内容

## 功能迭代

- {功能点标题}：{一句话说明，信息量大的可用二级子列表展开}

## 工程与平台迭代

- {功能点标题}：{一句话说明}

## 文档与规范迭代

- {功能点标题}：{一句话说明}
```

### 6. 完成汇报

写入/合并完成后，向用户简要汇报：本次更新了哪些文件（新建/合并）、各文件下新增或修改了哪些编号小节标题，方便用户快速核对是否有遗漏或分类错误。

## 注意事项

- 首份日志建立之前 `docs/iteration/` 目录不存在属正常情况，直接按模板新建即可。
- 与 `kit-iteration-start` 配套使用：`kit-iteration-start` 在迭代收尾时会自动调用本 skill 补全记录；本 skill 也可独立触发。
- 本项目开发日志存放在学城（外部），与仓库内迭代日志互补但互不同步内容：学城日志偏叙事，仓库日志偏结构化条目。
