# 编辑闹钟后，历史与未来的行为边界

## 现象

日历模式的提醒（周期闹钟）在修改信息后，比如把「每周二」改成「每周四」：

- **已经真正响过铃的日期**：不会被改写。当时周二响过了就是响过了，不会变成周四再响一次。
- **日历上显示的历史**：会跟着新规则变。改完再翻回过去的月份，历史格子会显示成周四——看起来「历史被改了」，但只是按当前规则实时重算的显示结果，并不代表当时周四真的响过。

## 为什么

代码分两层，行为边界由架构决定：

### 通知层（真实响铃）—— 历史不可变

- 数据库只有 `alarms` 和 `alarm_adjustments` 两张表（`src/db/schema.ts`），**没有「已响记录」**，响铃是发生过即消失的事件。
- 编辑闹钟时（`src/store/alarm-store.ts` 的 `updateAlarm`）流程是：更新数据库 → `cancelAlarmNotifications` 取消该闹钟全部未来通知 → `scheduleAlarmNotifications` 按新规则重新调度。已触发的通知不在调度范围内，天然不会被「改回去」。

### 显示层（计划页日历）—— 实时重算

- 日历不是历史回放。`getCalendarInstances`（`src/services/calendar.ts`）对任意日期范围（**包括过去的日期**）调用 `computeRingDatesInRange`，用当前规则重新推算。
- 所以规则一改，过去和未来都按新规则渲染，历史显示「跟着变」。

## 补充边界

- 这种「跟着改」是**全量、双向**的：改规则既影响未来，也影响历史显示，没有「只改本次 / 只改以后」的选项。
- weekly（按星期）类型没有单日 skip/add 调整；只有 cycle（按间隔周期）类型的 `alarm_adjustments` 是按具体日期落库的，skip 某一天不会影响其他日期。

## 如果将来要「改规则不改历史」

两个候选方案，按成本从低到高：

1. **规则生效日期**：给 alarms 增加 `valid_from` 字段，渲染历史范围时用旧规则（需要保留规则版本，或简单粗暴只渲染 valid_from 之后的实例）。
2. **响铃快照**：落一份「实际响过」的记录表，日历历史展示快照而非重算。成本最高，但语义最准。

## 结论

这是当前架构下的**已知设计取舍**：响铃历史以「不落库、不回放」为准，日历以「当前规则实时重算」为准。用户问「历史的会不会跟着改」，准确答案是：**真实响铃不会，日历显示会**。
